River Discharge & Nutrient QA Report

Output of ocean-prep/cli/river_final_check.py — a pre-production sanity check for the EMORID river discharge/nutrient pipeline (the real historical record, the nutrient climatology files, and the CMIP6 delta-change projected flow files), run across all 3 models x 2 scenarios. See the Data Quality Checks guide for what this tool is and how to run it yourself.

This is a point-in-time report (generated 2026-10-25) — re-run the script for current data before trusting these specific numbers going forward.

Summary

6 finding(s):

  • ⚠️ historical/EMORID_1993_2024_conc_nemo_TALK_DIC.nc: 155 site(s) have real discharge earlier in the record but go to EXACTLY zero for the last 30 days of coverage – a real river does not permanently stop flowing. By country: {‘Denmark’: 155}
  • ⚠️ historical/EMORID_1993_2024_conc_nemo_TALK_DIC_noleap.nc: 155 site(s) have real discharge earlier in the record but go to EXACTLY zero for the last 30 days of coverage – a real river does not permanently stop flowing. By country: {‘Denmark’: 155}
  • ⚠️ GFDL-ESM4/ssp126: daily file’s own Q_mean differs from the monthly file’s Q_mean by more than 25% for 96% of sites (median ratio 0.41) – the daily disaggregation claims to be mass-conserving per month; this is NOT.
  • ⚠️ GFDL-ESM4/ssp370: daily file’s own Q_mean differs from the monthly file’s Q_mean by more than 25% for 95% of sites (median ratio 0.43) – the daily disaggregation claims to be mass-conserving per month; this is NOT.
  • ⚠️ future/ssp126 (cross-model): 44 (model, site) pair(s) differ from the cross-model median Q_mean by more than 3x
  • ⚠️ future/ssp370 (cross-model): 48 (model, site) pair(s) differ from the cross-model median Q_mean by more than 3x

Root cause: GFDL-ESM4 daily mass-conservation finding (investigated 2026-10-25)

Not a code bug — a stale output file. Re-running the real disaggregation code (lib/river/disaggregation.py’s build_daily_shape_climatology + apply_daily_shape_disaggregation) directly against the real EMORID historical record and GFDL’s current monthly projection file reproduces the monthly file’s own Q_mean almost exactly (3619 vs 3637 m³/s for the worst-affected station, E12) — the algorithm itself is correct and genuinely mass-conserving.

The on-disk river_flows_future_ssp126_daily.nc is simply older than the monthly file it’s supposed to match:

filelast regenerated
GFDL-ESM4/ssp126 monthly (river_flows_future_ssp126.nc)2026-10-23 16:27
GFDL-ESM4/ssp126 daily (river_flows_future_ssp126_daily.nc)2026-09-23 16:29 (not regenerated since)
MPI-ESM1-2-HR/CNRM-ESM2-1 monthly + dailyboth 2026-09-23/24 (stayed in sync)

The Oct 23 regeneration log for GFDL confirms a plain river-projection run with no --disaggregate flag — it only rewrote the monthly and nutrient-load files, leaving the daily sibling stale. Nothing in the pipeline currently flags a monthly/daily regeneration going out of sync; that’s the real gap river_final_check.py’s daily-vs-monthly check now catches.

Fix: re-run river-projection --model GFDL-ESM4 --scenario ssp126 --disaggregate (and ssp370) to regenerate the daily files against the current monthly data.
