Root cause: GFDL-ESM4 daily mass-conservation finding (investigated 2026-10-25)#

Not a code bug — a stale output file. Re-running the real disaggregation code (lib/river/disaggregation.py’s build_daily_shape_climatology + apply_daily_shape_disaggregation) directly against the real EMORID historical record and GFDL’s current monthly projection file reproduces the monthly file’s own Q_mean almost exactly (3619 vs 3637 m³/s for the worst-affected station, E12) — the algorithm itself is correct and genuinely mass-conserving.

The on-disk river_flows_future_ssp126_daily.nc is simply older than the monthly file it’s supposed to match:

filelast regenerated
GFDL-ESM4/ssp126 monthly (river_flows_future_ssp126.nc)2026-10-23 16:27
GFDL-ESM4/ssp126 daily (river_flows_future_ssp126_daily.nc)2026-09-23 16:29 (not regenerated since)
MPI-ESM1-2-HR/CNRM-ESM2-1 monthly + dailyboth 2026-09-23/24 (stayed in sync)

The Oct 23 regeneration log for GFDL confirms a plain river-projection run with no --disaggregate flag — it only rewrote the monthly and nutrient-load files, leaving the daily sibling stale. Nothing in the pipeline currently flags a monthly/daily regeneration going out of sync; that’s the real gap river_final_check.py’s daily-vs-monthly check now catches.

Fix: re-run river-projection --model GFDL-ESM4 --scenario ssp126 --disaggregate (and ssp370) to regenerate the daily files against the current monthly data.
