Gridded 2D Validation Guide#

Overview#

gridded-2d-validation compares any horizontal 2-D model field against a gridded observation product. Three layer modes are supported:

LayerDescriptionTypical use
surface2-D field or top of 3-D outputSST, SSS, SSH
bottomDeepest wet cell of 3-D outputBottom temperature / salinity
<depth_m>Horizontal slice at a fixed depth (m)Depth-layer climatology

Multiple layers can be run in a single invocation.

There are five shipped configs: gridded_2d_validation.yaml is the generic one, with any combination of layers via --layers. gridded_2d_validation_surface.yaml, _bottom.yaml and _depths.yaml are the dedicated single-purpose variants used for NSe. _amm7_nemo.yaml targets a NEMO AMM7 (GFDL-ESM4-forced) run instead of pyGETM — only model.variable_map/model.base_path differ; see that file’s own header for its current (sample-data-only) status.

Prerequisites#

  • Model NetCDF output accessible via config/sources.yaml (see below), or directly via model.base_path / model.filename_pattern
  • A gridded observation file (local or Copernicus Marine / WOA)
  • pip install -e . with the ocean-post package

Model source: --source / --experiment / --model / --scenario#

Model input is NSe’s surf_bott_daily.nc (surface: temp_0/salt_0, bottom and depth slices: temp/salt), located via config/sources.yaml:

# Surface, CMEMS run
gridded-2d-validation --config config/gridded_2d_validation_surface.yaml --source CMEMS --experiment run01 --years 2010 2011

# Bottom, WOA run
gridded-2d-validation --config config/gridded_2d_validation_bottom.yaml --source WOA --experiment run01 --years 2010 2011

# Surface, CMIP6_raw run — forcing WITHOUT bias correction (e.g. ssp126)
gridded-2d-validation --config config/gridded_2d_validation_surface.yaml --source CMIP6_raw --model GFDL-ESM4 --scenario ssp126 --experiment run01 --years 2010 2011

CMIP6 is bias-corrected forcing; CMIP6_raw is not — use CMIP6_raw for raw-forcing runs such as ssp126; --source CMIP6 points at a folder that does not exist for that model/scenario.

--experiment is the run folder name, and the output label becomes <SOURCE>/<experiment>, or <SOURCE>/<model>-<scenario>/<experiment> for CMIP6/CMIP6_raw.

Config file (generic, multi-layer)#

# config/gridded_2d_validation.yaml
area: NS
experiment: Baseline   # overridden by --experiment when --source is used
years: [2010, 2011, 2012]

model:
  # Location, layout and variable names come from config/sources.yaml
  # (use --source). See the section above.
  name: "pyGETM"
  filename_pattern: "surf_bott_daily.nc"
  layout: explicit_file
  subdir:
    CMEMS: "{experiment}"
    WOA: "{experiment}"
    CMIP6: "{model}/{scenario}/{experiment}"
    CMIP6_raw: "{model}/{scenario}/{experiment}"
  run_model: GFDL-ESM4     # CMIP6 / CMIP6_raw run: overridden by --model
  run_scenario: ssp126     # CMIP6 / CMIP6_raw run: overridden by --scenario
  time_offset_days: -1
  variable_map:
    temp: sst        # rename model variable if needed

variables: [temp]

observations:
  temp:
    - name: OSTIA
      path:
        source: copernicus
        dataset_id: METOFFICE-GLO-SST-L4-REP-OBS-SST
        variable: analysed_sst
      offset: -273.15

processing:
  layer: surface              # single layer (default)
  # layers: [surface, bottom, 50]   # or multiple — CLI: --layers surface bottom 50
  chunking:
    enabled: true                # opt-in lazy/dask-chunked model loading; off by default
    time_chunk: 30              # days per processing chunk
    spatial_chunk: null          # or {lat: 50, lon: 50}

output:
  analyses_dir: "${OCEANICU_ANALYSES_FOLDER}"   # no default — see below

output.analyses_dir has no default#

There is no ./analyses fallback. The value is expanded from OCEANICU_ANALYSES_FOLDER in this machine’s data-roots file (<hostname>_ocean-post_data_roots.yaml), or set directly with --analyses-dir. If neither is set, the run stops with an error naming the missing variable.

Usage#

# Surface only (config default)
gridded-2d-validation --config config/gridded_2d_validation_surface.yaml --source CMEMS --experiment run01 --years 2010 2011

# Surface + bottom in one run (generic config)
gridded-2d-validation --config config/gridded_2d_validation.yaml --source CMEMS --experiment run01 \
    --layers surface bottom

# Surface + 50 m depth slice + bottom
gridded-2d-validation --config config/gridded_2d_validation.yaml --source CMEMS --experiment run01 \
    --layers surface 50 bottom

The --layers flag overrides processing.layer/processing.layers in the config.

Output#

Results are written to <OCEANICU_ANALYSES_FOLDER>/areas/<area>/validations/<SOURCE>/<experiment>/ (or .../<SOURCE>/<model>-<scenario>/<experiment>/ for CMIP6/CMIP6_raw):

plots/physics/pyGETM/<period>/
    surface/        ← time-mean maps, monthly bias maps, scatter plots
    bottom/
    50m/
tables/physics/pyGETM/
    <variable>_validation_statistics.txt

Statistics text files contain overall + monthly RMSE, bias, MAE, and correlation.

Generating residuals for MLE comparison#

gridded-2d-validation can write matched obs/model pairs as a parquet file for use with mle-comparison. One file is written per layer:

<OCEANICU_ANALYSES_FOLDER>/areas/<area>/validations/<SOURCE>/<experiment>/surface_residuals.parquet
<OCEANICU_ANALYSES_FOLDER>/areas/<area>/validations/<SOURCE>/<experiment>/bottom_residuals.parquet
<OCEANICU_ANALYSES_FOLDER>/areas/<area>/validations/<SOURCE>/<experiment>/0050m_residuals.parquet

Enable in the config (disabled by default to avoid large files):

output:
  save_residuals: true
  spatial_thinning:
    stride: 5        # keep every 5th grid point in both lat and lon
    time_stride: 1   # keep every N-th time step (1 = all)
    max_rows: 100000 # hard cap per parquet; excess rows are randomly sampled

The parquet schema is identical to profile residuals (time, lat, lon, depth, value, model_value, variable) so mle-comparison accepts it directly:

# Compare experiments using gridded surface obs
mle-comparison --analyses-dir $OCEANICU_ANALYSES_FOLDER --area NS \
    --obs-types surface --variables TEMP PSAL

# Combine gridded surface obs with Argo profiles
mle-comparison --analyses-dir $OCEANICU_ANALYSES_FOLDER --area NS \
    --obs-types surface argo --variables TEMP PSAL

Thinning is important. A 0.1° North Sea grid with daily SST obs has millions of rows, almost all spatially correlated. Without thinning the MLE independence assumption is badly violated. Start with stride: 5 and max_rows: 100000; tune until Δlog L values are stable across stride choices. See the Scope section of guides/mle-comparison.md for a full discussion.

Notes#

  • Observations are regridded onto the model grid using bilinear interpolation (xESMF); weight files are cached by MD5 hash under regrid_weights/.
  • For bottom layer: the deepest non-NaN cell is selected per column using sigma-coordinate-aware extraction.
  • For depth slices: the model field is interpolated vertically to the requested depth before regridding.

Performance: chunked loading and the materialize-once rule#

processing.chunking.enabled: true opens the model files lazily (dask-backed) instead of reading them fully into memory up front — needed for long multi-year runs (e.g. 13-14 years of daily OSTIA SST) where eager loading would otherwise hold the whole period in RAM at once.

Once loaded lazily, the model array is materialised exactly once (.load()), right after it’s masked/aligned with the observations and before any of the statistics passes (overall stats, per-year stats, monthly stats, scatter/map plots) run against it. This matters because every one of those passes calls .values/.compute() on whatever array it’s handed — on a dask-backed array that forces a fresh read from disk every time, not just once. Before this was fixed (commit 2b2d2b9), a 14-year OSTIA SST run re-read the full dataset 15-30+ times and took 5+ hours on HPC; the single up-front .load() eliminates that amplification while keeping the lazy-open memory benefit for the initial read itself.

For gridded_2d_validation_depths.yaml (multiple processing.layers depth values in one run), the same model file would otherwise be re-opened and re-read from scratch once per depth layer. A per-(variable, file) cache (_raw_model_cache, commit f988bec) keeps the raw per-year arrays across the --layers/processing.layers loop so each file is only read once regardless of how many depth layers are requested.

If you add a new statistics pass or plot that consumes model_da (or the raw per-year model arrays), make sure it reads the already-materialised/ cached array rather than re-opening or re-.compute()-ing a fresh lazy copy — that’s exactly how this bug was reintroduced.

Observations: regrid before materialising, not after#

The obs side has its own, separate cost: for a Copernicus-sourced dataset (OSTIA), load_observations() returns a dask-backed array over Copernicus’s remote ARCO/Zarr store — actual network transfer only happens when something forces .compute(). Materialising that array used to be forced onto dask’s synchronous (single-core) scheduler, with no regridding done first — meaning the single-threaded step decoded the full native-OSTIA-resolution array (over the model’s bounding box) rather than the much smaller, already-regridded model-grid array.

Whenever there’s no vertical layer to extract first (the surface case, and any obs product with no depth dimension at all — OSTIA/CCI-SST/ OISST/CCI-SSS all qualify), the obs is now regridded while still lazy, before materialising at all: xESMF’s regridder accepts a dask-backed DataArray directly (confirmed against the installed xesmf 0.9.2 — BaseRegridder.__call__ documents dask input, and _prepare_for_xesmf’s only values-forcing line never fires on a dask array, which has no .flags attribute). The regrid target is model (not yet time-sliced into model_da) — regridding only needs its horizontal lat/lon coordinates, which the later time-slicing never changes. Materialising the regridded (model-grid-sized) result then runs under dask’s default (parallel) scheduler, not the forced single-core one. _prepare_obs() takes an already_regridded flag so it skips regridding a second time.

The one case that still materialises-then-regrids, unchanged: a genuinely 3-D obs product (e.g. WOA profiles) being validated against a bottom/depth-slice layer — the depth slice has to be extracted on the obs’s own native vertical grid first, which needs real values, so that path is left exactly as it was.

Caching note: cache.enabled: true avoids re-fetching Copernicus data on a warm cache (the exact dataset/domain/time-range combination already has a local file under cache.dir on this machine). On a cold cache — e.g. the first time a given run executes on a machine whose CACHE_ROOT has never seen it before, even if the same validation has run many times elsewhere with a different CACHE_ROOT — the fetch still happens for real. There’s also a known gap in ocean-data’s DataLoader._load_copernicus(): on a cache miss it writes the fetch to the local cache file but then returns the original remote lazy object rather than reloading from the file it just wrote, so a cold-cache run can end up fetching the same data over the network twice. Not yet fixed.

Diagnosing a slow run: --verbose/--debug, and wall vs. CPU time#

Job 12762 (2026-10-23, 13 years NSe/OSTIA on SLURM) took 14+ hours and hit its walltime limit, with the per-run log showing only a single “Computing statistics in chunks…” line, then nothing, for 13+ hours. At INFO level (the default), neither compute_time_mean_chunked() nor compute_statistics_chunked() logged anything between a chunk loop’s start and its end — the only progress indicator was tqdm’s bar, which is unreliable in a non-tty SLURM log (it’s either silent or produces inconsistently-rendered lines depending on tqdm’s tty detection). Working out what had actually happened took scp-ing the job’s raw .out/.err files and a ps snapshot history off HPC and reconstructing a timeline by hand.

Both chunked loops now log a real line per chunk, every run, so that reconstruction is never necessary again:

  time-mean chunk 37/95: 52.1s
  stats chunk 12/95: 488.3s

Pass --verbose (alias --debug) for one more level of detail — each chunk line also reports wall-clock time vs. CPU time actually used:

  stats chunk 12/95: wall=488.3s cpu=9.1s (2% busy -- low % here means
  something else was competing for the machine, not this code)

This is the single most useful diagnostic for exactly the situation job 12762 was in: wall time close to CPU time means the chunk’s own computation is genuinely the bottleneck (a real code/algorithm problem, worth profiling further); wall time far exceeding CPU time — as turned out to be the case here — means the process was mostly waiting, not computing, which points at something external (I/O contention, or, as confirmed afterwards from ps evidence, another long-running process already occupying the same “exclusive” SLURM node before this job even started). --verbose applies to every ocean-post CLI script (added in add_common_arguments()), not just this one.
