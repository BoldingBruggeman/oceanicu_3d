  # ocean-data review (branch `claude`, read-only; nothing modified)
  
  Baseline: 294 tests pass in 48 s. Findings marked "verified" were reproduced by running the code on synthetic data; the rest are from reading the code.
  
  ## Overall assessment
  
  - The package works on its tested paths, but the core helpers every loader relies on are untested and have real bugs. `data_utils.subset_domain`, `subset_time` and `match_lon_convention` have no tests in any repo; neither do the DataLoader cache functions, `NetCDFLoader`, `regridding` or `spatial_interp`.
  - The worst bug is in `subset_domain`: its 1-D path broadcasts every non-spatial variable over lat/lon and turns ints into floats. This is very likely the true cause of the "13 GB time_bnds" problem that `esgf_loader.py` works around in two places and blames on the source files.
  - `load_model_data` has three loading paths (eager single file, eager directory, NetCDFLoader lazy/glob) that return different variable names, dimensions and error behaviour for the same file.
  - The DataLoader cache can return the wrong data: the covering-cache lookup matches on a 40-character prefix that drops ensemble member, table and the Copernicus frequency suffix.
  - There is no Kelvin detection or unit conversion anywhere in ocean-data. `temperature_variables` / `is_temperature` exist but nothing calls them, so that concern lives in the siblings.
  - Duplication is heavy: the ERDDAP stack is copied four times (Argo, ICES, EMODnet, EMODnet-chemistry) and cache-key/cache-write logic about eight times.
  - `data_loader.py` (2211 lines) is four modules in one: URI dispatch, cache, source checking, and a legacy local-file loader that duplicates `NetCDFLoader`.
  - Comment rot is concentrated in `esgf_loader.py` and `data_loader.py`. `CLAUDE.md` is stale ("There are no tests", a `config_mappings.yaml` that does not exist).
  - Packaging: ocean-data, ocean-plot and ocean-post all install a top-level package named `cli`, and `config/` is not shipped as package data.
