# Good DIC/TA open boundaries for NSe (CMIP6 vs CMEMS)

## Context

A screenshot comparison (5 days into a 2010 run: upper = CMIP6-sourced
config, lower = CMEMS-sourced config) shows a considerable difference in
DIC near the open boundaries -- most visible at the Kattegat/Baltic
segment -- and a smaller but real difference in TA.

A `final-boundary-check` run (ocean-prep) against the real NSe bio
boundary files found the pipeline otherwise clean (one negligible
negative po4 value, already patched in place to its absolute value and
re-verified). That check only validates boundary *files* in isolation
(NaN/range/magnitude-vs-reference/calendar) -- it does not compare
CMIP6 vs CMEMS against each other, which is the actual question here.

Direct investigation into why the two screenshots differ turned up
**two separate, real effects**, of very different size -- both must be
accounted for before concluding anything about boundary *value* quality:

1. **Historical DIC/TA bridge method differs between sources, but only
   modestly.** Neither CMIP6's nor CMEMS's own real dissic/talk product
   reaches back to 2010 (CMIP6's deltachange file starts 2015-01-01;
   CMEMS's bio_carbon_new starts 2024-07-29), so both splice in a
   historical bridge file for 2010-2014
   (`driver/oceanicu_providers.py`'s `_dic_ta_historical_method_param`
   / `_dic_ta_hist_file` dict, ~line 1451). CMEMS's config
   (`NSe/config/nse_cmems.yaml:547`) explicitly sets
   `dic_ta_historical_method: pml_trend` (a real secular-trend
   extrapolation + Baltic salinity regression, Partridge et al. 2025
   coefficients). CMIP6's config (`NSe/config/nse_cmip6.yaml`) never
   sets this key at all, so it silently gets the default,
   `cycled_climatology` (a flat day-of-year climatology with no trend,
   generated by a since-deleted scratchpad script). Directly compared
   both bridge files' real surface values at day 6 of 2010, per segment,
   on bb-server1: differences are real (segment 7/Kattegat: DIC
   1666.5 vs 1574.5 mmol/m3, TA 1676.3 vs 1613.3; other segments: DIC
   ~2200 vs ~2140-2180, TA within ~35) -- consistently a few percent,
   not an order of magnitude. Real, worth fixing, but not big enough by
   itself to be *the* story behind a "considerable" visual difference.

2. **FABM initial condition is NOT apples-to-apples between the two
   screenshotted runs -- this is almost certainly the dominant effect.**
   `nse_cmip6.yaml:715` sets `fabm.ERSEM.restart_file:
   ${FABM_RESTART_FOLDER}/restart_ersem.nc` -- a real, already
   spatially-resolved ERSEM state from a prior spin-up, covering DIC/TA
   too (`_seed_fabm_state_from_restart` in the generated driver code).
   `nse_cmems.yaml:643` sets `restart_file: null`, EXPLICITLY documented
   (lines 628-639) as "round 1 of a perpetual spin-up cycle... no
   restart_ersem.nc exists yet" -- so the CMEMS run in the screenshot
   starts FABM, including DIC/TA, completely flat and uniform from
   `fabm_ersem.yaml`'s own scalar `initial_value`, with zero spatial
   structure anywhere in the domain. Comparing day-5 fields between
   "already spun up" and "flat start" is not a clean test of boundary
   quality -- near the boundary, where SPONGE relaxation hasn't had time
   to overwrite the uniform interior yet, this asymmetry alone would
   produce exactly the kind of sharp, boundary-adjacent visual
   discrepancy in the screenshot, independent of anything about the
   boundary files themselves.

The plan below (a) neutralizes the IC confound so a future comparison
is actually measuring boundary quality, and (b) fixes the one real,
quantified boundary-side issue found (the bridge-method mismatch), as
the two concrete, grounded steps before any deeper DIC/TA
bias-correction work is justified.

## Approach

1. **Unify the historical bridge method.** Add
   `dic_ta_historical_method: pml_trend` to `NSe/config/nse_cmip6.yaml`'s
   `boundaries.fabm.CMIP6` block (same key CMEMS already sets). The
   CMIP6-range file this needs, `bio_carbon_pml_trend_20100101_20141231.nc`,
   already exists in `${BOUNDARY_FOLDER_FABM_CMEMS}` on bb-server1 --
   no new file generation needed, this is a one-line config change.
   Regenerate the affected experiment(s)' driver scripts so the splice
   actually picks it up.

2. **Neutralize the IC confound before re-judging the screenshots.**
   Either (a) run CMEMS's own round 2 (it already has `--save-restart`
   wired per the "round 1" comment -- run it once, then point
   `nse_cmems.yaml:643`'s `restart_file` at the resulting
   `restart_ersem.nc`, same as CMIP6 already does), or (b) for a faster,
   purely diagnostic A/B, temporarily point BOTH configs at the SAME
   restart file (or both at `null`) for one short comparison run, purely
   to isolate the boundary-driven signal from the IC-driven one. (a) is
   the real, durable fix; (b) is only for verifying step 1's effect
   cleanly without waiting on a fresh spin-up.

3. **Re-run the 5-day comparison** (same plotting setup that produced
   the original screenshot) with both confounds controlled (pml_trend on
   both sides, same IC state) and inspect the Kattegat/segment-7 region
   specifically, since that's where both real effects found above are
   largest.

4. **If a real discrepancy still remains** after 1-2 (i.e. the genuine,
   post-bridge-period DIC/TA from CMIP6's raw ESM-derived deltachange/
   directbc boundary data disagrees substantially with CMEMS's real
   bio_carbon_new at the same calendar dates, post-2024-07-29, where both
   have real coverage to compare against), that points at CMIP6's raw
   ESM absolute DIC/TA being regionally biased at this boundary --
   expected for global ESMs in a brackish, poorly-resolved shelf sea --
   and the fix is extending the SAME bias-correction methodology already
   built for this exact problem (`derive_historical_dic_ta.py`'s
   Partridge et al. coefficients, and the existing `run-direct-bc-boundaries`
   method already used for other bio vars) to explicitly cover dissic/talk
   against a real reference, rather than inventing a new correction
   scheme. This step is exploratory and should only be scoped in detail
   once steps 1-3 show whether a real gap remains.

5. **Make this a standing check, not a one-off screenshot.** Extend
   `ocean-prep/cli/final_boundary_check.py` (or `boundary-diagnostics`)
   with a CMIP6-vs-CMEMS cross-source comparison for dissic/talk at
   matching dates/segments where both have overlapping real coverage,
   so a future regression here shows up as a failing check instead of
   requiring another manual screenshot comparison.
